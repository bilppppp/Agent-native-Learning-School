## 目标：控制“有多少任务尚未完成”

你已熟悉函数和 Promise。还需要补上一个边界：调用函数可能立即开始工作，Promise 是对结果的表示，不是等待启动的许可证。

```js
const promises = urls.map(url => fetch(url));
await Promise.all(promises);
```

在执行 `map` 时，`fetch` 已逐个被调用。`Promise.all` 观察这些 Promise；它不负责限制请求的启动。p-limit 则接收**还没调用的函数**，只在有空槽时调用它。一个槽从获准执行开始占用，直到返回的结果成功或失败才释放。第 3 课会细化“占槽”和函数体开始之间的微任务间隔。

这里的并发是生命周期重叠，不等于多线程同时执行 JavaScript。异步任务等待 I/O 时，其他任务可继续，但等待中的任务仍未完成。p-limit 不把同步 CPU 工作搬到别的线程。

## 先预测，再看一个时间线

以下是**课程生成的理想模型**，不是仓库性能实测。任务 A/B/C/D 按顺序提交，耗时分别为 60/20/30/10ms；无额外开销，限额 `C=2`。先想：B 完成后，必须等 A 吗？

| 时间 | 槽中的任务 | 发生的事 |
| --- | --- | --- |
| 0 | A、B | C、D 等待 |
| 20 | A、C | B 完成，C 补位 |
| 50 | A、D | C 完成，D 补位 |
| 60 | 无 | A、D 完成 |

串行需要 `60+20+30+10=120ms`，此安排需要 60ms。不是每凑齐两个任务，就等这一组全部结束再处理下一组；空槽一出现就可补位。若使用 `Promise.all`，最终数组仍按提交顺序 A/B/C/D 对应，不按完成顺序排序。

这个模型还能推导下界：总耗时 `T >= max(最长单任务耗时, 总任务耗时/C)`。理由分别是单个任务不可被槽拆短，以及 C 个槽在 T 时间里最多提供 `C*T` 的工作时间。本例下界为 `max(60,120/2)=60`。下界不是一般保证：若耗时是 50/50/50、两个槽仍需要 100ms，而下界只有 75ms。真实系统还有网络、资源竞争和调度开销。

## 常见误解：两个槽就是每秒两个请求

不是。若每个任务 10ms，一个槽也可能在一秒内连续完成很多次；若一个任务要 10 秒，它会长时间占槽。固定并发限制约束同时未完成的数量，不保证固定时间窗内的请求数。仅在任务耗时近似固定、槽持续忙碌的理想情形，可用 `吞吐量约为 C/平均耗时` 做粗估，这不是 API 保证，更不是限流器的替代品。

## 核心问题与活动

- 创建一个 Promise 与“把工作交给 limiter”有何不同？
- 等待网络返回时，任务是否仍占槽？
- 为什么不能直接把总耗时除以并发数当成精确预测？

活动：把上例 A 的耗时改成 80ms，其他不变，画两个槽的时间线，再用自己的话说明 `Promise.all` 负责什么。可选用 `/activities/limit-lab.mjs` 的 `schedule` 模式观察受控启动；没有运行环境就用纸面状态表。
