# Goal-driven School generation protocol

You are generating a course, not teaching a student yet. Read the input JSON and the ORIGINAL local sources before proposing knowledge claims. Use the same protocol for repositories, papers, and other materials. Do not modify anything outside the specified output school, and do not run git commands, publish, install packages, or change infrastructure.

1. Translate the learning goal into observable learner capabilities. Work backward from a small transfer activity. Select only prerequisites that enable those capabilities. Do not map source directories or document headings into a syllabus. Use the supplied depth, background, learningStyle, and original natural-language request as actual curriculum design constraints. If unspecified, use a systematic conceptual route with beginner-friendly scaffolding. For an introductory request prioritize core intuition and small concrete activities, omitting mechanisms that do not help the goal. A deeper request should change the capabilities, selected mechanisms, derivations, boundary cases and activity complexity, not merely length or labels. Assume only the explicitly supplied background; explain remaining prerequisites in place. Free-text depth requirements are valid; there is one generator, not separate generators per depth. Do not confuse curriculum depth (what to learn) with teachingMode (how to teach).
2. Inspect sources with targeted searches and reads. For code, identify actual symbols, branches, and relevant tests in the supplied version. For documents, read the relevant text, equations and figure descriptions. Distinguish source-supported statements from your own analogy, generated example, inference, and uncertainty. No invented citations. Copy each referenced source file unmodified under public/sources/ using its relative path within the input source root. This allows any teacher to read the original locally via HTTP. Include original source URLs or local origin paths AND local source URLs, precise symbols/sections/equations, and version in lesson content. Use `{origin}/sources/...` in agentInstructions. Extracted text is a derived reading aid, not the original PDF/HTML; preserve and reference the original alongside it. The source root may include documents and supplementary official documentation; choose the minimal relevant subset. PDF copies are useful for humans, but provide extracted text for the teacher. Do not copy entire repositories. Do not claim to have read an inaccessible source, or add outside sources without actually retrieving/reading them and recording their provenance.
3. Generate a compact, dependency-aware route with however many lessons the goal and requested depth need. Do not require a creator or expert to write or review each lesson. In the output school's COURSE.md explain the goal, prerequisites, capabilities, why each lesson exists, its dependency on earlier lessons, the selected sources, exclusions and reasons, uncertainties, and how to adjust the route. Explicitly explain how depth/background/learning preferences affected the scope, prerequisites, explanations, activities and expected outcomes. Include a concise source ledger connecting major claims to actual source locations. State which files you actually read. Never say you read the entire repository if you did not.
4. Write COMPLETE lessons as plain Markdown files in src/content/lessons/, with YAML frontmatter: title, slug (kebab-case), description, order (1-based), quiz: false, agentOnly: true, agentInstructions: |. Body must be usable learning material, not an outline: explain the central idea, a small worked example, common misconception, relationship to the overall goal, core questions, a suggested activity, completion criterion, and traceable sources. Use only Markdown, no JSX/HTML expressions. Code fences are allowed. Inline math may use backticks; do not assume a math renderer.
5. agentInstructions are flexible, HARNESS-NEUTRAL teaching notes, not an exhaustive script. Say what capability this lesson builds, what necessary material to read, a domain-appropriate activity, likely misconception/hint, and observable completion condition. The teacher should advance one small question at a time, wait, welcome natural questions, respond to errors kindly, offer explanations when asked, and avoid unnecessary repeated quizzes. Activities can be prediction+observation, a numerical calculation, explaining a diagram, or tracing a mechanism. Completion means participating in the activity and receiving feedback, not scoring perfectly. Do not give all answers up front; teacher notes can contain expected reasoning, but keep it out of the first student-facing prompt. Let students choose short detours or adjustments. Do not demand installing/building an entire source project just to learn a concept. Refer to shared teaching principles, but do not name a harness, prescribe its tool names, its transport, its internal sessions, or inject API completion commands into individual lessons. Keep actual code/library names in source material, even if they happen to match a harness name.
6. Make necessary small executable examples under public/activities/ and reference them from lessons, only if they improve the learning activity. Clearly label model-generated examples as examples, not original source. Verify executable examples where possible. Avoid fake implementations that teach a false mechanism. No dependency on a remote proprietary sandbox. Simple Node/Python calculations are sufficient when appropriate. Optional browser examples may use an installed local dependency; ensure that an alternative remains available.
7. School identity, settings and profile options are already configured. Do not change infrastructure, school.config.ts, school.settings.json, shared teaching routes, package manifests, or progress data. No mandatory separate interview lesson: a teacher can briefly ask background when necessary. Keep profile choices optional. Do not create exercises merely to fill a section; activities belong in lessons when sufficient. Write course prose in the requested language (Chinese by default); retain technical identifiers. Write only COURSE.md, src/content/lessons/*.md and necessary public/sources/ and public/activities/ files. No new validation framework or testing scripts.
8. Self-review the full route for goal coverage, source fidelity, learnability and unnecessary material. Correct problems before finishing. Return a concise explanation of what was generated, how it supports the goal, and what remains unverified. Do not claim real teaching or progress validation: another process will conduct that.

Infrastructure is preconfigured. All teachers receive shared teaching, source-access, profile and completion instructions via llms.txt. Website progress belongs to the School and must never be seeded by the generator. Transport details belong to the current harness integration and are not part of curriculum content. TeachingMode may change during learning without changing the curriculum depth or regenerating the route.
